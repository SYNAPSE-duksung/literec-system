# UI QA 피드백 (2026-07-12)

`npm run dev`로 앱을 직접 구동하고 Playwright(headless Chromium, 390×844 모바일 뷰포트)로 로그인 → 회원가입 → 온보딩 → 홈 → 검색 → 게시판 → 리뷰 작성 → 리뷰 상세(좋아요/싫어요) → 마이페이지 → 책 상세까지 전체 화면 흐름(섹션 3)을 클릭으로 재현하며 확인했다. 콘솔 에러(`console`/`pageerror`)는 전 구간에서 0건이었다. 아래는 코드까지 대조해서 원인을 확인한 이슈다.

## 1. (버그) 리뷰 제출 후 "뒤로가기"를 누르면 방금 낸 빈 작성 폼으로 돌아감

**재현**: 게시판 → `기록하기` → 내용 입력 후 `기록 올리기` → 리뷰 상세로 이동 → 상단 `뒤로가기` 클릭.
**결과**: 게시판이 아니라 방금 제출했던 `기록 남기기` 화면이 **빈 폼 상태로** 다시 나타난다. 한 번 더 뒤로가기를 눌러야 게시판으로 돌아간다.

**원인**: [App.tsx](../app/src/App.tsx) 의 `navigate()`가 화면 전환 시 무조건 `history`에 push만 하고, 리뷰 작성 → 제출 → 상세처럼 "완료된 입력 화면"으로는 다시 돌아갈 필요가 없는 흐름에서도 replace를 하지 않는다.
```
board → (기록하기) → reviewWrite → (제출) → reviewDetail
뒤로가기 1번 → reviewWrite (❌ 빈 폼, 사용자 입장에서 의미 없는 화면)
뒤로가기 2번 → board (✅ 기대했던 화면)
```
섹션 3 흐름도의 "제출 → 게시판/상세로 이동" 의도와 어긋나는 내비게이션이다. `onCreated`로 이동할 때는 `navigate` 대신 history의 마지막 항목을 교체(replace)하는 처리가 필요해 보인다.

**상태**: 수정 완료. `App.tsx`에 history를 push하지 않는 `replace()`를 추가하고, 리뷰 작성 완료(`onCreated`) 시 이를 사용하도록 변경. 리뷰 상세에서 뒤로가기 1번으로 게시판으로 바로 돌아가는 것을 재현 테스트로 확인.

## 2. (기능 결함) 게시판의 "기록하기"는 어떤 책을 리뷰하는지 고를 수 없고 항상 목록 첫 번째 책으로 고정됨

**재현**: 게시판 탭에서 바로 `기록하기` 클릭 (책 상세를 거치지 않고 진입).
**결과**: 항상 `book_001("섬의 아이")`에 대한 리뷰 작성 화면이 뜬다. 다른 책을 선택할 UI가 없고, 지금 어떤 책에 대해 쓰는지 안내도 없다(카드에 표지/제목이 나오긴 하지만 "왜 이 책인지" 사용자가 알 방법이 없음).

**원인**: [App.tsx:154-157](../app/src/App.tsx)
```ts
onWriteReview: () => {
  const defaultBookId = allBooks[0]?.id ?? '';
  navigate({ name: 'reviewWrite', bookId: defaultBookId });
},
```
책 상세(`BookDetailPage`)에서 들어가는 "기록 남기기"는 정상적으로 해당 책 id를 넘기지만, 게시판에서 들어가는 진입점은 책을 고르는 절차 없이 목록 첫 항목으로 하드코딩되어 있다. 리뷰 작성이 "어떤 책"에 대한 기록인지가 핵심인 앱 성격상, 책 검색/선택 단계가 빠진 것은 단순 버그를 넘어 기능 누락에 가깝다.

**업데이트**: 기록 남기기 진행 시 책 검색을 통해 선택하도록 기능을 추가한다.

**상태**: 수정 완료. 게시판에서 책 지정 없이 `기록 남기기`로 진입하면(`bookId`가 빈 문자열) `ReviewWritePage`가 `useBooks()` 기반 검색·선택 화면을 먼저 보여주고, 책을 고른 뒤에만 기존 작성 폼으로 넘어가도록 변경. 이 경로에서는 "다른 책 선택" 링크로 다시 검색 화면으로 돌아갈 수 있음. 책 상세에서 특정 책으로 진입하는 기존 흐름은 그대로 유지(검색 화면 생략).

## 3. (일관성/접근성) 모든 입력 필드의 `label`이 `id` 없이 렌더링되어 label-input 연결이 끊어짐

[Input.tsx](../app/src/components/common/Input.tsx), [Textarea.tsx](../app/src/components/common/Textarea.tsx)는 `htmlFor={id}`로 라벨을 연결하도록 만들어져 있지만, 실제 호출부(`LoginPage`, `SignupPage`, `BoardPage`, `SearchPage`, `ReviewEditor` 전부)에서 `id`를 한 번도 넘기지 않는다. 결과적으로 `htmlFor={undefined}`가 되어:
- 라벨 텍스트를 클릭해도 해당 입력창에 포커스가 가지 않음
- 스크린리더가 라벨과 입력을 연결하지 못함

컴포넌트 자체는 올바르게 설계되어 있으므로, 호출부에서 `id`만 채워주면 되는 간단한 수정이다.

**상태**: 수정 완료. `LoginPage`, `SignupPage`, `BoardPage`, `SearchPage`, `ReviewEditor`, 그리고 새로 추가된 리뷰 작성 책 검색 입력까지 모든 `<Input>`/`<Textarea>` 호출부에 고유 `id`를 부여.

## 4. (일관성) 책 상세 / 리뷰 상세 헤더 타이틀이 잠깐 깜빡였다가 바뀜

책 상세, 리뷰 상세로 진입하는 순간 상단 헤더에 "책 상세" / "리뷰 상세"라는 fallback 문구가 약 300ms 노출된 뒤 실제 책 제목으로 바뀐다. (`App.tsx`에서 `title = headerBook?.title ?? '책 상세'` 형태로, `useBook`/`useReview`의 mock 비동기 지연 동안 fallback이 그대로 보임.)

반면 홈/게시판/검색/마이페이지 탭은 고정 문자열이라 이런 깜빡임이 없고, 본문 영역은 로딩 중 "불러오는 중이에요" 같은 명시적 로딩 상태를 보여준다. 헤더만 로딩 처리 방식이 다른 화면들과 다르게 동작해 화면마다 로딩 경험이 일관되지 않다.

**상태**: 수정 완료. `App.tsx`에서 `useBook`/`useReview`의 `isLoading`을 헤더 타이틀 계산에 반영해, 로딩 중에는 사실과 다른 fallback 문구("책 상세"/"리뷰 상세") 대신 빈 문자열을 보여주도록 변경. 데이터가 도착하면 바로 실제 제목으로 채워짐.

## 5. (설계 원칙과의 정합성) 책 표지 이미지가 외부 서비스(placehold.co)에 실시간으로 의존함

`mock/books.ts`의 모든 `coverUrl`이 `https://placehold.co/...` 실제 네트워크 요청이다. 응답 자체는 정상(200)이지만:
- 이미지 래퍼에 배경색 등 placeholder 스타일이 없어(`object-fit: cover`만 지정) 로딩 지연 시 깨진 이미지 아이콘이 그대로 노출됨 (직접 캡처로 확인).
- 오프라인/사내망 등 외부 요청이 막힌 환경에서는 표지가 전혀 렌더링되지 않음.

`CLAUDE.md`와 명세서 섹션 1이 강조하는 "의존성 최소화 / mock 기반" 원칙에 비춰보면, 로컬 정적 이미지나 CSS로 그린 플레이스홀더로 대체하는 편이 프로토타입의 자기완결성(self-containment)에 맞다.

**상태**: 코드 확인 결과 `book-card__cover`, `book-detail-page__cover`, `review-write-page__cover`, `similar-book-card__cover`에 이미 `background: var(--color-border)`가 지정되어 있어, 이미지가 늦게 뜨는 동안에도 빈 박스가 아니라 브라우저 기본 깨진 이미지 아이콘이 겹쳐 보이는 정도로 완화되어 있었음(최초 보고서의 "배경색 placeholder 없음" 서술은 부정확했던 것으로 확인, 정정). 다만 `placehold.co` 실시간 의존 자체(오프라인 시 전혀 렌더링 안 됨)는 별도 결정 사항이라 이번 변경에는 포함하지 않음 — 로컬 정적 이미지로 교체할지 여부는 별도로 논의 필요.

## 7. (회귀, 우선순위 높음) 리뷰 작성용 "책 검색" 화면에서 하트 버튼을 누르면 마이페이지 "좋아한 책"에도 추가됨

**재현**: 게시판 → `기록하기` (책 미지정 진입) → 책 검색 목록에서 카드 우상단 하트 아이콘 클릭 → 마이페이지 이동.
**결과**: 카드를 클릭해 책을 "선택"한 게 아니라 하트를 눌렀을 뿐인데, 마이페이지의 "좋아한 책" 개수가 실제로 증가한다(재현 테스트로 확인: 2개 → 3개).

**원인**: 이번 1차 수정에서 책 선택 화면을 새로 만들며 기존 `BookCard`를 그대로 재사용했는데, `BookCard`에는 항상 좋아요 하트 버튼이 포함되어 있다([BookCard.tsx](../app/src/components/book/BookCard.tsx)). "리뷰할 책 고르기"라는 이 화면의 목적과 무관한 "책 좋아요" 액션이 같은 카드에 함께 노출되어, 사용자가 의도치 않게 다른 기능(마이페이지 찜 목록)을 건드리게 된다. 같은 컴포넌트를 다른 맥락에 재사용할 때 그 맥락에 맞지 않는 부가 기능까지 함께 따라온 경우다.

**제안**: 리뷰 작성 책 검색 화면에서는 하트 버튼을 숨기는 옵션을 `BookCard`에 추가하거나(`showLikeButton` 등), 이 화면 전용으로 표지+제목+작가만 보여주는 더 단순한 카드를 쓰는 편이 목적에 맞다.

**상태**: 수정 완료. `BookCard`에 `showLikeButton?: boolean`(기본 `true`) prop을 추가하고, 리뷰 작성 책 검색 화면에서만 `showLikeButton={false}`로 하트 버튼을 숨김. 재현 테스트로 책 선택 후에도 마이페이지 "좋아한 책" 개수가 그대로인 것을 확인.

## 8. (구조적 일관성) 로그인/회원가입 화면과 그 이후 화면의 "뒤로가기" 패턴이 서로 다름

로그인 이후 모든 화면(책 상세·리뷰 작성·리뷰 상세)의 뒤로가기는 [Shell](../app/src/components/shell/Shell.tsx)의 상단 고정(sticky) 헤더 바 안에, 타이틀과 한 줄로 나란히 배치된다([TopHeader.tsx](../app/src/components/shell/TopHeader.tsx)). 반면 [SignupPage](../app/src/pages/SignupPage.tsx)는 인증 이전 화면이라 `Shell`을 거치지 않고 자체적으로 뒤로가기 버튼을 구현하는데, sticky 헤더 바 없이 좌상단에 버튼만 따로 떠 있고 그 아래 큰 제목(`<h1>회원가입</h1>`)이 별도 텍스트로 이어진다.

기능은 동일("이전 화면으로")하지만, 사용자가 배우는 시각적 패턴이 두 가지(고정 헤더+인라인 back / 여백 위 단독 back+큰 제목)로 나뉘어 있다. 인증 전/후 레이아웃 전환이라는 구조적 이유는 이해되지만, 회원가입도 `TopHeader`와 같은 시각 언어(구분선, sticky, 아이콘+제목 정렬)를 재사용하면 화면 전환에 대한 일관된 기대를 유지할 수 있다.

**상태**: 부분 수정. `UI_DESIGN_SPEC.md` 섹션 6.2가 회원가입 화면의 레이아웃을 "[뒤로가기 아이콘]" 한 줄 다음 "회원가입 / 부제" 두 줄 제목으로 명시하고 있어(`TopHeader`의 아이콘+제목 한 줄 배치와 다름), 레이아웃 구조 자체를 `TopHeader`로 통합하는 것은 스펙 위반이라 보류했다. 대신 스펙과 상충하지 않는 범위에서:
- 로그인/회원가입 화면에 다른 모든 화면과 동일한 `max-width: 390px` 컨테이너(`--container-max-width`)와 배경색을 적용해, 앱 전체에서 화면 폭·배경이 어긋나 보이던 부분을 통일함.
- 회원가입 뒤로가기 버튼의 색상(`color: var(--color-primary)`)과 정렬(`display: flex`)을 `TopHeader`의 뒤로가기 버튼과 픽셀 단위로 동일하게 맞춤(기존엔 우연히 상속된 색상에 의존하고 있었음).

## 9. (접근성 일관성) 카드형 리스트 아이템이 `role="button"`이지만 키보드로 실행되지 않음

`BookCard`, `ReviewCard`는 `<Card role="button" tabIndex={0} onClick=...>`로 시맨틱상 버튼처럼 선언돼 있어 Tab으로 포커스는 가능하지만, `onKeyDown` 핸들러가 없어 포커스된 상태에서 Enter/Space를 눌러도 아무 반응이 없다. 직접 재현(Playwright로 카드에 포커스 후 `Enter` 전송)한 결과 헤더 타이틀이 "결"(홈)에 그대로 머물러 이동이 발생하지 않음을 확인했다.

반면 앱의 다른 모든 상호작용 요소(`PrimaryButton`, `Button`, `ToggleChip`, `BottomNav`, `TopHeader`의 뒤로가기/검색 버튼)는 실제 `<button>` 엘리먼트라 키보드로 정상 실행된다. 같은 "클릭 가능한 항목"인데 카드류만 키보드 사용자에게는 실제로 눌리지 않는 버튼처럼 보이는 셈이라, 접근성 측면에서 화면 간 상호작용 방식이 일관되지 않는다.

**제안**: 카드 컴포넌트에 `onKeyDown`으로 Enter/Space 시 `onClick`을 호출하는 처리를 추가하거나, 클릭 가능한 카드 전체를 `<button>`/`<a>`로 감싸는 방식으로 통일.

**상태**: 수정 완료. 각 카드 컴포넌트(`BookCard`/`ReviewCard`/`SimilarBookByReviewCard`)마다 `role="button" tabIndex={0}`을 반복 선언하던 것을 걷어내고, 공용 [Card.tsx](../app/src/components/common/Card.tsx) 자체가 `onClick`을 받으면 자동으로 `role="button"`, `tabIndex={0}`, Enter/Space → `onClick` 위임을 처리하도록 변경. 앞으로 새 카드가 추가돼도 같은 패턴을 다시 구현할 필요 없이 자동으로 키보드 접근성을 갖춘다. Playwright로 카드에 포커스 후 `Enter`를 눌러 실제 이동이 발생하는 것을 확인.
